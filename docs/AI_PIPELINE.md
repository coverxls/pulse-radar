# AI 链路：Prompt、评测与降级

这个项目里 AI 不是用来「生成」，而是用来**判定**：给一条搜索结果，判断它是否真实、与监控词的相关性有多高、重要程度如何、一句话说清它和关键词的关系。这类任务看起来简单，实际最容易出两类问题——**语义相近但主题不同被误判为相关**，以及**模型输出不稳定导致整条链路崩掉**。下面是我在这两点上的处理。

## 1. 任务拆成两段：召回与判定

```
关键词 ──查询扩展──▶ 5~15 个变体 ──字面预匹配──▶ 命中/未命中 ──▶ 模型判定 ──▶ 阈值门控
```

- **召回段**（便宜、可解释）：模型把 `Claude Sonnet 4.6` 扩展成 `Claude Sonnet` / `sonnet 4.6` / `claude-sonnet-4.6` 等变体，用来做字面匹配。没有 Key 时退化为「按分隔符切词 + 两两组合」，仍然可用。
- **判定段**（贵、主观）：只对真正进入候选池的内容调用模型，并且把召回段的结论作为提示传进去。

把两段分开的好处是：召回错了可以看变体列表，判定错了可以看分数和理由，不用去猜一个黑盒为什么给了 83 分。

## 2. Prompt 设计要点

完整 Prompt 在 `server/src/services/prompts.ts`，核心是三条：

**(1) 给分档而不是只给布尔值。** 输出 `relevance: 0-100`，业务层用阈值决定去留。阈值可以随时调（`50` / `65`），不用改 Prompt，也不会把历史判断作废。

**(2) 把「字面是否命中」注入 Prompt。** 这是效果提升最明显的一处：

```
注意：文本预匹配发现内容中未直接提及关键词"Claude Sonnet 4.6"的任何变体，请特别严格审核相关性。
```

模型看到这句，会把「同领域但没提关键词」的内容压到 40 分以下；没这句话时，它经常因为「都在讲 AI 编程」给出 80+。

**(3) 用示例化的评分锚点，而不是抽象的「相关/不相关」。**

```
- 仅仅属于同一领域但未提及关键词 → 低于 40
- 直接讨论、提及或有实质关联 → 60 以上
- 只是间接沾边（同类产品、同领域不同主题）→ 30~50
```

配合 `temperature = 0.2`，同一输入的分数波动明显收敛。

输出要求严格 JSON，业务层用正则截取首个 `{...}` 再解析，并对字段做类型与范围兜底（`relevance` 夹在 0~100，`importance` 必须属于四个枚举值，`summary` 截断到 150 字）。

## 3. 评测：11 例分层评测集

`server/src/__tests__/aiRelevance.test.ts` 里维护了一组标注样本，分三类：

| 类别 | 例子 | 断言 |
| --- | --- | --- |
| 直接相关（3 例） | 关键词 `Claude Sonnet 4.6`，正文是它的发布新闻 | `relevance ∈ [80,100]`，`keywordMentioned = true`，最终保留 |
| 同领域不同主题（4 例） | 关键词 `Claude Sonnet 4.6`，正文是 GPT-5 发布 | `relevance ≤ 50`，最终过滤 |
| 边界（4 例） | 提到 Claude 但是 Haiku、只提品类不提型号 | 分数落在中间区间，按阈值过滤 |

每个用例同时校验三件事：分数区间、`keywordMentioned`、以及「按线上阈值门控后是否会被保留」。最后一条最重要——它保证评测和线上行为是同一套判据，而不是测一套、跑另一套。

跑法：

```bash
# 不配置 Key：只跑确定性的部分（查询扩展、预匹配、降级），AI 用例自动 skip
pnpm --filter @pulseradar/server test

# 配置 Key：真实调用模型，输出逐例报告与通过率
OPENROUTER_API_KEY=sk-or-... pnpm --filter @pulseradar/server test
```

配置 Key 时会额外跑一个「评估报告汇总」用例，打印每例的分数、预期区间和通过情况，并要求整体通过率 ≥ 80%——改 Prompt 后跑一遍就知道有没有退化。

需要说明的是：**11 例只能防明显退化，不等于严谨的基准**。样本是我从自己关心的几个关键词（模型版本、编程工具）里挑的代表性场景，覆盖不到长尾。真要上线给多人用，这里至少要扩到几百例并区分领域。

## 4. 三级降级：宁可少判，不可中断

| 情况 | 处理 | 用户可见结果 |
| --- | --- | --- |
| 没配 `OPENROUTER_API_KEY` | 跳过模型，按预匹配结果给基础分（命中 50 / 未命中 20） | 能收到热点，但没有真假判断与摘要 |
| 调用失败（超时/429/5xx） | 指数退避重试 2 次，仍失败则降级为命中 30 / 未命中 10 | 同上，`relevanceReason` 标记为「AI 分析失败」 |
| 返回无法解析 | 抛错 → 走同一降级路径 | 同上 |

降级不是「静默失败」：`aiUsage.failures` 会计数，日志里带模型名与 Prompt 版本，`GET /api/health` 能看到累计失败数。

## 5. 版本与成本

- Prompt 放在独立模块，带 `PROMPT_VERSION`（当前 `2026-03-analysis-v2`），每次调用都打到日志里。这样「上周效果变差」能直接定位到是不是换了 Prompt。
- 成本控制：每个关键词最多 25 条进入模型、正文截断 2000 字符、`max_tokens = 500`、每批 3 并发、查询扩展结果缓存。按一次扫描 10 个词估算，单轮模型调用在百次量级。
- 模型可配（`OPENROUTER_MODEL`），默认用便宜且中文表现稳定的 `deepseek/deepseek-v3.2`；判真假这种任务没必要上最贵的模型。

## 6. 下一步能做什么

1. **两阶段判定**：先用便宜的 embedding 算相似度粗排，只把 Top-N 交给大模型精判，成本能再降一个量级。
2. **Few-shot 注入**：把评测集里最容易错的样例做成 few-shot 示例，比继续调措辞更有效。
3. **一致性校验**：同一内容跑两次，分数差超过 15 就标记为不稳定样本，人工复核后回流评测集。
4. **用反馈闭环**：前端加「不相关」按钮，把用户否决的样本自动加入负例集——个人工具里这是最便宜的数据来源。
