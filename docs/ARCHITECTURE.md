# 架构说明

## 1. 系统边界

PulseRadar 是一个**单用户、可自托管**的信息雷达：一个 Node 进程负责抓取/判定/推送，一个前端负责看和管，一个 SQLite 文件存数据。没有消息队列、没有缓存中间件、没有鉴权——这是刻意的：个人工具优先保证「一台 1C1G 的机器能跑起来」，复杂组件按需要再加。

```
┌─────────────────┐        REST /api/*         ┌──────────────────────────┐
│  React 控制台    │ ─────────────────────────▶ │  Express 5 API (:3001)   │
│  (Vite :5173)   │ ◀───────────────────────── │  + Socket.io             │
└─────────────────┘   WebSocket  hotspot:new    └───────────┬──────────────┘
                                                            │ Prisma
                                                ┌───────────▼──────────────┐
                                                │  SQLite (dev.db)         │
                                                └───────────▲──────────────┘
                                                            │
                              ┌─────────────────────────────┴───────────────┐
                              │  扫描编排 hotspotChecker（cron / 手动触发）  │
                              └───┬───────────┬───────────┬─────────────────┘
                                  │           │           │
                            ┌─────▼───┐ ┌─────▼────┐ ┌────▼─────┐
                            │ 搜索源   │ │ 中文源    │ │ Twitter  │
                            │ Bing/HN │ │ 搜狗/微博 │ │ API      │
                            └─────────┘ │ B站       │ └──────────┘
                                        └───────────┘
```

## 2. 一次扫描的完整链路

1. **取激活的监控词**：只扫 `isActive = true` 的词，暂停的词不产生抓取成本。
2. **账号识别**（可选）：如果关键词命中某个 B 站 UP 主，直接抓 TA 的最新视频，比泛搜更准。
3. **查询扩展**：把词扩展成 5~15 个变体（大小写、连字符、中英文对照、缩写），结果进程内缓存，同一关键词不重复调用模型。没有 API Key 时退化为纯文本拆分（按空格/连字符切词 + 两两组合）。
4. **并行抓取**：`Promise.allSettled` 同时打六个源，任何一个超时/被反爬都不影响其他源；单源结果条数、失败原因都写进日志。
5. **归一化去重**：URL 去掉末尾斜杠、统一 `www.`，再按首次出现去重。
6. **新鲜度过滤**：丢弃发布时间超过 7 天的内容；没有发布时间的搜索结果保留（搜索引擎通常不给时间）。
7. **来源优先级 + 配额**：Twitter 排在前面且允许 15 条，其余来源共享 10 条——避免搜索结果里全是同一个来源，把模型预算花在信息密度更高的地方。
8. **预匹配 + 模型判定**：先做字面匹配，把「命中的词」作为提示传给模型；模型返回 `isReal / relevance / keywordMentioned / importance / summary` 的结构化 JSON。
9. **阈值门控**：
   - `isReal = false` → 丢弃；
   - `relevance < 50` → 丢弃；
   - 关键词未在正文出现且 `relevance < 65` → 丢弃（这条专门治「同领域不同主题」）。
10. **落库 + 推送**：写 Hotspot、写 Notification，按 `keyword:{text}` 房间 emit，`high/urgent` 再发邮件。

本地实测的一次真实扫描（关键词 `DeepSeek Harness`，未配置 AI Key）：

```
Bing 10 · Sogou 8 · Bilibili 20 · HackerNews 0 · Weibo 0 · Twitter 0
38 raw → 38 unique → 38 fresh → 入库 10 条
```

> 没有 Key 时相关性打分走规则降级（预匹配命中给 50 分），所以这一步只能验证「抓取-去重-入库-推送」链路；真假识别与细粒度打分需要配置 `OPENROUTER_API_KEY`。

## 3. 数据模型

| 表 | 作用 | 关键约束 |
| --- | --- | --- |
| `Keyword` | 监控词 | `text` 唯一；`isActive` 控制是否参与扫描 |
| `Hotspot` | 抓到的热点 | `@@unique([url, source])` 保证幂等；冗余了互动数据与作者信息 |
| `Notification` | 通知记录 | 与 Hotspot 弱关联（`hotspotId` 可为空），删除热点不删通知 |
| `Setting` | 键值配置 | `key` 唯一，前端设置页读写 |

`Hotspot` 把互动数据（点赞/转发/评论/弹幕/播放）摊平成列，是为了排序时能直接在 SQL 里算，不必再关联一张「指标表」；代价是来源相关的列会留空（只有 B 站有弹幕数）。

## 4. 关键取舍

| 决策 | 备选 | 为什么这么选 | 代价 |
| --- | --- | --- | --- |
| SQLite + Prisma | Postgres + Prisma | 零运维、单文件备份；个人规模（万级）完全够用 | 并发写会锁；换库要重做迁移 |
| Socket.io | SSE / 轮询 | 需要房间语义（按关键词分组推送）与自动重连 | 多一层协议封装，客户端体积略大 |
| 进程内 node-cron | Redis + BullMQ | 单实例部署，省掉一个中间件；任务本身就是「每 30 分钟扫一遍」 | 多实例会重复扫描；失败无重试队列 |
| HTML 抓取 | 官方 API | Bing/搜狗/微博/B 站没有便宜的公开 API | 依赖页面结构，改版即失效 |
| 同步循环 + 单飞锁 | 队列削峰 | 一次扫描量级小（几十条），锁住并发即可 | 长任务会阻塞该进程的其他调度 |

## 5. 失败模式与对策

| 失败 | 现象 | 当前对策 |
| --- | --- | --- |
| 模型超时/限流 | 整轮扫描卡住 | 两次指数退避重试；仍失败则规则降级，不中断 |
| 模型返回非 JSON | 解析异常 | 正则提取首个 `{...}`；再失败走降级 |
| 某个源被反爬 | 该源 0 条、日志打错误 | 单源 `allSettled` 隔离 + 每源独立限速器 + UA 轮换 |
| 定时与手动同时触发 | 重复抓取、浪费额度 | 单飞锁，后到的直接跳过并打日志 |
| 同一条内容重复入库 | 重复通知 | URL 归一化 + 唯一索引 + 落库前查重 |
| 进程被 kill | 数据丢失/连接泄漏 | SIGINT/SIGTERM 优雅退出：关 Socket、关 HTTP、断开 Prisma |

## 6. 成本控制

- **配额**：每个关键词最多 25 条进入模型（Twitter 15 + 其他 10）。
- **截断**：正文最多 2000 字符，避免长文把 prompt 撑爆。
- **缓存**：查询扩展结果进程内缓存，上限 200 条，超限淘汰最早一条。
- **并发**：`batchAnalyze` 每批 3 个并发，既快又不容易触发限流。
- **可观测**：每次调用记录模型、Prompt 版本、延迟、token；`GET /api/health` 暴露累计调用数与平均延迟。

## 7. 如果要做成产品

按依赖顺序：

1. **鉴权与多租户**：加 `userId` 字段 + JWT，扫描按用户拆分。
2. **数据源插件化**：抽出 `SourceAdapter`（`name / search(query) / health()`），用注册表装配，新增来源不改编排。
3. **任务队列**：扫描任务从进程内 cron 迁到 BullMQ，多实例也不会重复跑，天然带重试与死信。
4. **语义去重**：URL 只能挡完全相同的链接，跨平台转载要靠 SimHash 或 embedding 近似判重。
5. **可观测性**：接 OpenTelemetry + Prometheus，把「每个源的成功率、每轮耗时、每轮成本」变成面板。
